# `get_exchange_rate` 在干什么

位置：`crates/common/src/xrate.rs`。Cache 里换算账户货币时走这里（`Cache::try_get_xrate`）。

## 一句话

手里有一堆货币对的买卖价，问：**1 块 A 货币等于多少 B 货币。**

有直盘就用直盘。没有直盘，就借中间货币串起来。例如没有 EUR/JPY，但有 EUR/USD 和 USD/JPY，就算：

```
1 EUR = 1.1001 USD
1 USD = 110.01 JPY
所以 1 EUR = 1.1001 × 110.01 JPY
```

## 有什么用

交易系统里钱不是同一种货币。

- 账户是 USD，仓位是 EUR、BTC、JPY
- 算总资产、盈亏、保证金、风控，都得先换成同一种货币

行情通常只给交易对报价，不会给你「任意两种货币」一张完整表。这个函数就是那张表的现场拼装。

## 为什么不能 `map.get("EUR/JPY")`

1. 很多对根本没挂牌。EUR 兑 JPY 常常要走 USD。
2. 报价是单向的：有 EUR/USD，不一定有 USD/EUR。反过来要用倒数。
3. 买卖价不一样。你卖 EUR 拿 USD 用 bid；你买 EUR 花 USD 用 ask。方向反了，价差就反了。

所以不是查表，是走路：货币是点，报价是路，沿路把汇率乘起来。

## 为什么看起来麻烦

麻烦的不是公式，是这几件必须处理的脏事。

**1. 一张报价要铺成两条路**

`EUR/USD = 1.10` 的意思是 1 EUR = 1.10 USD。同时也就有了 1 USD = 1/1.10 EUR。不铺反向，USD→EUR 就断了。

**2. Bid / Ask / Mid 不能混用**

- Bid：你卖 BASE 能拿到的价
- Ask：你买 BASE 要付的价
- Mid：中间价，估值常用

反向必须用对侧：按 bid 卖掉，换回来应对着 ask 买。否则价差方向错，风控数字会偏。

**3. 可能有多条路，结果必须稳定**

EUR→USD 既可以直接走 EUR/USD，也可以 EUR→GBP→USD。DFS 碰到第一条就算。HashMap 遍历顺序一变，第一次碰到的路就变，回测同一笔单子汇率会跳。所以邻接表排了序：同一份报价，永远走出同一个数。

**4. 环不能转死**

EUR→USD→EUR→USD… 不标记访问就会转圈。每个货币只进一次。

**5. 坏报价不能把整个换算炸掉**

`"EURUSD"` 少了 `/`、价格是 0 或负数：跳过。走不到目标就返回「没有汇率」，让上层当暂无数据，而不是整个 Cache 报错。

## 函数怎么走（按代码顺序）

1. A 和 B 是同一种货币 → 直接 `1`。空盘口也一样，不用换。
2. 买卖报价有一边是空的，或条数对不上 → 报错。
3. `Last` / `Mark` 不是买卖盘，这里算不了 → 报错。
4. 每个 `"BASE/QUOTE"` 拆成正向边、反向边。
5. 从 A 出发 DFS，沿路相乘。走到 B 就返回乘积。走不到返回 `None`。

## 用测试数据把数算出来

报价：

- EUR/USD bid 1.1000 / ask 1.1002 → 中间价 1.1001
- USD/JPY bid 110.00 / ask 110.02 → 中间价 110.01

问 EUR 兑 USD、中间价：直连，`1.1001`。

问 USD 兑 EUR、中间价：反向，`1 / 1.1001`。

问 EUR 兑 JPY、中间价：没有直盘，EUR→USD→JPY，`1.1001 × 110.01`。

问 EUR 兑 JPY，但盘口里只有 EUR/USD：走不到，`None`。

## 它不保证什么

不保证最优汇率，也不保证最短路径。只保证：**同一份报价，算出同一个数。** 交易里这比「 theoretically 最划算的那条交叉盘」更重要。
